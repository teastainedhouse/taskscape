## 1. Stack and shape

| Question | Decision |
| --- | --- |
| API language | Node 22, plain JS (ESM, JSDoc types, no compile step) |
| Runtime dependencies | Exactly `pg` (loaded only for `postgres://` URLs) and `@modelcontextprotocol/sdk` (MCP server only). Tests use `node:test`; SQLite is `node:sqlite` |
| Databases | PostgreSQL in production; SQLite for local work and tests. One dialect-neutral migration serves both unless a `NNN_name.sqlite.sql` / `.postgres.sql` override exists |
| One door | The browser and the MCP server both call the HTTP API; only `api/lib/repo/*.js` runs SQL |
| MCP server | A local stdio script in `mcp/`, authenticated with a personal token |
| Who can edit | Everyone signed in; `permissions.edit` in the config narrows it to groups |
| Hosting | Host-neutral: `createApp()` takes a Web `Request`; each fork adds a thin adapter under `host/<its-host>/` (gitignored upstream). README shows the three adapter shapes |
| Look | Themes are CSS files, `public/css/theme-<name>.css`; the config names the default and the list; people pick on their profile page (see §8) |

**Data representation** (identical on both databases): ids are app-generated UUIDs in `TEXT` (the catch-all and seed use fixed readable ids); timestamps are ISO-8601 UTC `TEXT`; `due_date` is `YYYY-MM-DD` text; booleans are `INTEGER` 0/1 with a `CHECK`. No `SERIAL`, `BOOLEAN`, `TIMESTAMPTZ`, `AUTOINCREMENT`, or `RETURNING`: writes update, then select inside the transaction.

**Statuses live in the config, not a table**, so a team changes them without a migration. Rows keep whatever string they were written with.


## 2. Data rules (where the one-pager was silent)

1. **A private project only ever contains its owner's tasks, and every task belongs to exactly one project.** A catch-all project ("General", fixed id `config.catch_all_project.id`, created by `npm run migrate`, owned by the system principal) receives orphans. It is always public and cannot be made private, reassigned, or trashed; its name, description, status, and tags are editable. Making a project private (or reassigning a private project) moves every task in it owned by someone else, live or trashed, to the catch-all in the same transaction: `project_id` changes, `version` increments, an activity entry `update {"project_id": {from, to}}` is written by the flipping user, and nothing else on the task changes, with one exception: when a project that was already private changes owner, its tasks were hidden from everyone but their owner, so each moved task also becomes private, and the move never shows anyone a task they could not see before. The response carries `moved_tasks`, counting only tasks the caller could see. Every other door that could break the invariant refuses with 400: creating a task for someone else in a private project, reassigning a task inside one, moving someone else's task into one, and restoring a trashed task whose owner differs. A task created without a project goes to the catch-all. There is no undo: the moves are in the activity log, the moved tasks stay editable by their owners, and making the project public again lets anyone move them back by hand.
2. **Tags are a public, shared vocabulary.** Names and colors are visible to everyone, with no usage counts, so a tag attached only to private items reveals nothing about the items; creating a tag does write a public activity entry naming who made it, so the tag editor and the MCP tool descriptions say that tag names are seen by everyone. The MCP `tag` tool reads its target before creating any tag, so a hidden or missing target leaves none behind.
3. **Trashing a project does not stamp its tasks.** They disappear with the project and come back on restore. A task trashed on its own stays trashed after its project is restored.
4. **"Delete" means trash everywhere.** No hard delete, not even in the API. `ON DELETE CASCADE` on the tag join tables exists only for a future hard-delete migration.
5. **Tasks can move between projects** (`PATCH project_id`); the target must be visible to the caller and not trashed.
6. **Reassigning:** any editor can reassign a public item; only the owner can reassign a private one (only the owner can see it). After reassigning a private item, the previous owner gets 404 on it. **Nobody makes an item private for someone else:** create refuses it, and so does a PATCH that turns `private` on while handing the item over, since the new owner never chose to hide it. Making it private and then handing it over, two steps, is the owner's deliberate choice.
7. **Owners are ids plus a name snapshot.** Rows carry `owner_id` and `owner_name`; the name refreshes whenever the owner writes to their own item. **When the server knows the new owner, it names them:** under `password` the `users` table (§4) and under `dev` the configured users are a directory, so assigning to an id found there stores the directory's name and ignores the client's, and nobody can label an item "owned by bob" under a name of their choosing. Under `password` an item can only be given to an enabled user (a disabled or unknown id is refused alike), so a look-alike id cannot carry a borrowed name and a write cannot tell a disabled account from a made-up one; under `dev`, which is local, an unlisted id still takes the client's name. `system` is reserved under every provider. The directory lookup is the last check on a write, after the visible read, the version check, and every other refusal, so a missing, hidden, or stale target answers as it would without an owner, and only a write that would otherwise go through can tell a known id from an unknown one. Under `headers` there is no directory (identity arrives on every request), so the client's `owner_name` is still required and trusted. Items store the snapshot under every provider.
8. **Overdue is computed in the browser:** `due_date` before today's date and status not in `closed_statuses`, where "today" is in the time zone the person chose on their profile page, else the device's. The API offers only `due_before` / `due_after`. Claude has no device: the MCP `me` tool gives it the chosen zone, else the site default (`preference_defaults.time_zone`, UTC unless set).
9. **A project's `version` does not change when its tasks change**, so task edits never make project edits conflict.
10. **The hit counter has no deduplication**, like a 1996 counter, and stores no viewer identity. It is a `hit_count` column, not a views table: a table would record who looked at what, the one thing a privacy-respecting counter must not store. It is bumped only by the UI's project page, with a visible read first. A fork that wants deduplication adds `project_views(project_id, viewer_hash, day)` and increments the column only on a new row.
11. **Tag attach and detach bump the item's `version`** and require `version` in the body, like any other write to the item. **A request that would change no stored value is not a write:** attaching a tag that is already attached, detaching one that is not, or a PATCH whose fields all equal the stored ones. The version is still checked under the row lock (409 with `current` when stale), but it is not bumped, `updated_at` stays, no activity entry is written, and the current record comes back. A bump without an entry would break rule 13, and an entry with empty `changes` says nothing. The owner's name-snapshot refresh (rule 7) is a stored change: alone it is a logged `owner_name` update; next to other changes it stays out of the entry.
12. **Activity `changes`:** `create` lists every settable field as `{"to"}` (tags as names); `update` lists only changed fields as `{"from","to"}` (reassignment as `owner_id` + `owner_name`, privacy as `private`, tags as name arrays); `trash` and `restore` are `{}`. Titles are not stored on the entry; reads join the current name, so renamed or trashed items still read well.
13. **What is versioned and logged:** projects, tasks, their tag links, and comments. Deliberately outside that rule: the hit counter, the auth tables (`mcp_tokens`, `users`, `sessions`), and the `preferences` table, which have no `version` and write no activity entries. Preferences are personal settings (theme, what to call comments, shortcuts on or off, time zone): the last write wins, nobody else can be affected by them, and a history of someone's theme choices is not worth keeping or showing in What's New.


14. **Guestbook comments belong to their parent and their author.** A comment sits on one project or task and has no privacy of its own: it is visible exactly when its parent is (§3), so it cannot leak an item, and it needs no toggle that could disagree with its parent's. Any editor can sign a visible, live parent; signing is not an edit of the parent, so it never makes a parent edit conflict (as rule 9). Nobody edits a comment: what was signed stays as signed, and there is no edit history to keep. Only the author trashes and restores their own comment, each a compare-and-set on the comment's `version` with an activity entry; trashing needs no edit rights, so someone who lost them can still take their words back. A guestbook holds at most 500 live comments, so nobody can flood an item, its export, or a reader's context; an item's owner cannot remove someone else's words, only ask, and an author cannot take back what another wrote. A trashed comment shows only to its author, in the parent's guestbook, where Restore is; it stays out of the Trash page, which lists items. Trashing the parent closes its guestbook (no signing, no restores) without stamping the comments, as rule 3. **Activity entries name the parent, never the text** (`changes: {"on": {type, id}}`): an entry is permanent, so text copied into it would outlive the author trashing it. The accepted costs, because a comment's visibility follows only its parent: a project going private takes its guestbook with it, hiding comments even from the people who wrote them, who then cannot trash them either; handing a private item to someone else hands over its guestbook, the previous owner's own notes included. Letting authors reach their own comments regardless would need a read that skips the visibility predicate, which rule 3 of CLAUDE.md forbids outside a transaction after a visible read. A trashed comment's activity entries stay (they are the history, and carry no text). Search does not look in comments.

## 3. Privacy

**One place:** `api/lib/repo/visibility.js`. Every repo read takes `user` first and applies these; handlers contain no SQL, so forgetting the predicate is structurally hard and testable without HTTP. Helpers that skip the predicate are named `unsafe*`, never exported, and called only inside a transaction after a visible read.

```js
projectVisible(alias, user) // (alias.private = 0 OR alias.owner_id = ?)
taskVisible(t, p, user)     // task predicate AND its project's predicate
live(alias)                 // alias.deleted_at IS NULL
trashState(alias, mode)     // include_trashed: false | true | only
commentVisible(c, user)     // the comment's parent project or task is visible
commentShown(c, user)       // live, or the caller wrote it (trashed comments show only to their author)
```

Every task query joins `projects p` so both predicates apply. Default trash predicate: projects `live('p')`; tasks `live('t') AND live('p')`.

| Read path | Mechanism |
| --- | --- |
| get project / get task | `repo.*.get(user, id)` returns `null` for missing and invisible alike; the handler throws the same `notFound()` |
| lists, search, trash, export | the same `list(user, filters)` functions; filters stack on the predicate, never replace it |
| tags on items | loaded for the already-filtered id set; the global tag list carries no counts |
| activity | `EXISTS` subqueries against the item's current state (below) |
| people | distinct owners of items visible to the caller, plus the caller, plus, for an editor in the browser, the directory (a token therefore sees fewer names than its owner in the browser: the directory is for the owner picker and the import's name matching, which a token has no page for) (configured dev users under `dev`, enabled `users` rows under `password`, none under `headers`). The directory adds names, never anything about items; under `password` its ids are sign-in usernames, and failed sign-ins lock a username, so read-only accounts and tokens, which have no owner picker, do not get it; a name known only from a private item is never listed |
| guestbook comments | `commentVisible` on every read (list, get, export); the guestbook routes read the parent visibly first, so a hidden parent is the generic 404 |
| hit counter | `recordHit(user, id)` does a visible read inside the increment transaction |
| writes | visible read first inside the transaction; the 409 `current` is re-read visibly and becomes 404 if no longer visible |

**404, not 403.** Others see nothing of a private item: no placeholder, no count. A non-owner reaching one gets a body byte-identical to a nonexistent id's. 403 is used only when the caller can already see the item (a non-owner flipping `private`, a non-editor writing, a token principal on a human-only route). Error messages never echo ids, names, titles, or submitted values.

**Activity is filtered at read time against the item's current state:**

```sql
WHERE a.item_type = 'tag'
   OR (a.item_type = 'project' AND EXISTS (SELECT 1 FROM projects p
        WHERE p.id = a.item_id AND (p.private = 0 OR p.owner_id = ?)))
   OR (a.item_type = 'task' AND EXISTS (SELECT 1 FROM tasks t JOIN projects p ON p.id = t.project_id
        WHERE t.id = a.item_id AND (t.private = 0 OR t.owner_id = ?) AND (p.private = 0 OR p.owner_id = ?)))
   OR (a.item_type = 'comment' AND EXISTS (SELECT 1 FROM comments c
        WHERE c.id = a.item_id AND <commentVisible(c)>))
```

Consequences: flipping private hides all past entries from others, including the flip itself; flipping public reveals the full history (the UI toggle says so); moving a public task out of a private project into a public one reveals its history the same way (the task page asks first, and the MCP `update` description says to confirm it); reassigning a private item passes its history to the new owner and takes it from the old one (the owner editors ask first); a project going private hides its tasks' entries; trash state does not affect activity visibility. Snapshotting owner and privacy on each entry was rejected because old public entries would keep leaking an item after it went private.

**Not encryption.** Anyone with database or hosting admin access reads every row; README says so.


## 4. Identity

`getUser(request, ctx)` in `api/lib/auth/index.js` returns a `Principal` (typedef there) or `null`:

1. **Bearer token** (`Authorization: Bearer tsk_…`) is authoritative when present: SHA-256 the value and look it up among unrevoked `mcp_tokens`; unknown or revoked is 401 and never falls through to the provider or a cookie. Success yields `via: 'mcp'` with `session_id` from `X-Taskscape-Session`; a token write without that header is 400. Token principals get 403 on `/api/tokens/*` and on the hit counter, so a leaked token cannot mint tokens. Under `password`, a token works only while a live `users` row exists for its user. A token's edit rights follow the groups snapshotted when it was issued.
2. **The configured provider** (`auth.provider`, overridable by `TASKSCAPE_AUTH_PROVIDER`):
   - `headers`: identity from headers a sign-in layer injects, or from one base64-JSON principal header read with dot paths. Safe only behind a layer that overwrites client-supplied copies; README says so in bold.
   - `password` (added 2026-11-01): Taskscape's own sign-in for hosts without one. Users are managed from the shell (`npm run users`), never through the web; sessions are cookie-backed rows. Decisions: scrypt hashes with a bounded number running at once; an in-memory, per-process lockout per username (and a separate one for password changes); `__Host-` cookie, not extended by use; changing a password signs out other sessions and can revoke tokens; adding a user whose id already owns items needs `--claim-existing`, so a new account cannot silently inherit someone else's history. **Active sign-ins** (2026-11-02): the profile page lists the caller's own live sessions (`GET /api/me/sessions`, created, last seen, expires, the current one marked) and ends one or all the others; these are human-only and self-scoped like the token routes, someone else's session id is the generic 404, and the cookie value and its hash never leave the server. There is no MCP tool: a token is not a session and must never end one. The table keeps no user agent or address, so the list names only times; a column for either was judged not worth a migration and a new piece of stored tracking.
   - `dev`: the user from `X-Dev-User`, else the `taskscape_dev_user` cookie, else `auth.dev.default_user`; must be a configured dev user. Refused when `TASKSCAPE_ENV=production`; the UI shows a red DEV MODE banner.
3. `null` is 401. The API never redirects; under `headers` the host's sign-on handles page loads, and under `password` the pages send signed-out visitors to `login.html`.

**Cross-site writes** from any browser principal are refused (`Sec-Fetch-Site`, JSON-only bodies); Bearer tokens are exempt.

`can_edit`: `permissions.edit = "everyone"` is true; `"group"` needs an overlap between the user's groups and `permissions.groups`. Minting a token requires `can_edit`.


## 5. Database adapter

- **Placeholders:** repo SQL uses `?`; `placeholders.js` rewrites to `$1..$n` for PostgreSQL, skipping string literals and comments.
- **Compare-and-set:** `UPDATE … SET version = version + 1 WHERE id = ? AND version = ?`; zero rows changed means 409 with the current record. The activity entry is written in the same transaction.
- **Transactions:** SQLite uses `BEGIN IMMEDIATE` behind a per-process mutex; PostgreSQL checks out a pool client and passes a client-bound `Db`. Nested transactions throw. Where a write must see a concurrent privacy flip, it takes the project's row lock first with a no-op `UPDATE`.
- **Migrations:** numeric order, one transaction per file, recorded in `schema_migrations`. Two files sharing a number, a misnamed `.sql`, or an applied file renamed all throw. Run by `npm run migrate` as a deploy step, never at request time; PostgreSQL holds an advisory lock around the run.
- **Configuration:** `TASKSCAPE_DATABASE_URL` picks the adapter by scheme. Secrets live in the environment, never in `taskscape.config.json`.


## 6. MCP server

- **Transport:** stdio. `mcp/tools.js` is transport-free (plain JSON Schema plus handlers), so a fork can switch to an HTTP transport by changing `server.js` only.
- **Session:** a random id per server process, sent as `X-Taskscape-Session`; the API records it with `via = 'mcp'` on every write, so What's New shows which Claude session did what.
- **Data, not instructions:** the server instructions and every tool description say that titles, descriptions, notes, tag names, and owner names are user data, never directions. Results are JSON text, not prose.
- **One item per delete:** the `delete` tool takes a single id, refuses arrays, and tells Claude to confirm each item with the user. It trashes a project, a task, or a comment the token's owner wrote.
- **Comments:** `get` returns the item with its newest 50 `comments` (and `comments_omitted` when there are more), and the `comment` tool adds one. Comment text is other people's words, so it carries the same data-not-instructions notice as every other field. The MCP server says "comments" everywhere; "guestbook" is a flavour of the UI's words that a person can choose, not a concept of the API.
- **Dates mean the user's calendar:** a `me` tool returns the token's user with their preferred `time_zone` and `today` in it, and the server instructions say to call it before working with dates. A tool was chosen over stamping the zone into every result: date context costs one small call when it matters, and never pads a list of tasks. Due dates are calendar days in that zone; the server stores no times of day for them.
- **Errors never throw:** a 409 comes back as `isError` text naming both versions with the current record embedded, so Claude can retry without another read. A 404 says the item may be private to someone else.
- **No tool for** the hit counter (reading through MCP is not a visit) or for the human-only routes (tokens, sign-in, password changes).


## 7. Testing

- `node:test`, no framework. `test/helpers.js` builds an in-memory SQLite app (or uses `TASKSCAPE_TEST_POSTGRES_URL`) and calls `app.fetch` directly: no ports, parallel-safe.
- One test file per concern (the file names say which). Privacy tests compare 404 bodies byte for byte against a random id's.
- `ui-escaping.test.js` greps `public/` and fails on `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, inline `on*=`, or `javascript:`.
- Not covered by tests: rendering, the marquee, the click-to-edit flow. Check those by hand (or with a scripted browser) against the seed data (§9).


## 8. UI

- Plain HTML, CSS, and ES modules served as-is; DOM built only with the `textContent` helpers in `public/js/dom.js`.
- `base.css` holds layout, focus rings, and the `prefers-reduced-motion` kill switch; `theme-<name>.css` holds a look (every page links the default, `js/theme.js` swaps in the person's choice). Nostalgia stays in the chrome and pixel details; the content area stays readable, with visible focus and the reader's dark mode.
- **Hit counter** (`js/odometer.js`, loaded with `import()` so a content blocker costs only the counter): a `role="img"` span with an `aria-label`, one `.digit` per zero-padded digit (six minimum). `project.html` calls `POST /hit` once after the project loads; if that fails the page still shows the record's `hit_count`. Three clicks within two seconds reveal the webring bar (from `config.webring`; hidden when empty). On private projects a `title` says only the owner's visits are counted.
- **Overdue is said in still text.** Wherever the toolbar marquee appears (home, project), a static line in the page names the count and links each overdue task (the first ten, then "and N more"). The count asks the API for open statuses only, at the largest page size, and says "N+" when that page comes back full. The marquee repeats it as decoration only: plain text, `aria-hidden`, stopped under `prefers-reduced-motion`, and stoppable by anyone with a toolbar Stop button (remembered per browser in `localStorage`, wrapped in try/catch). A screenshot, a screen reader, a keyboard user, or a reduced-motion reader never depends on it.
- **My tasks** (`mine.html`) is the one view across projects: `GET /api/tasks?owner=me`, no API of its own. Closed statuses are hidden by asking for the open ones (`status=` every status not in `closed_statuses.task`), so a row whose status was renamed out of the config shows only with "Show closed tasks". Overdue tasks come first under a static count. "Owner: Me" on the home page still filters projects, not tasks.
- **Editing happens by clicking the value** (`js/inline-edit.js`, one module for every page): the project header; every field on the task page; status, owner, due date and private in the project's task table; status and due date in My tasks (tags keep their chip editor everywhere, and the title is a link). The value is a real button (Tab reaches it, Enter or Space opens the editor), so it is a control and not a trick on a span. Escape cancels; Enter, or leaving the field, saves when the value changed; a textarea saves with Ctrl/Cmd+Enter or on leaving; a select saves when a pointer picks an option, while the keyboard steps through options and saves with Enter or Tab (on some platforms a closed select changes on every arrow press, and each of those must not be a write); a checkbox saves when it changes. Each save is one `PATCH` of that one field with the version the value was drawn with (not whatever the page holds when the save runs), so two people editing different fields never conflict, a stale edit meets a 409, and the 409 goes through `attempt()` and redraws the current record. Focus returns to the value after a key-driven save or cancel; a save that happened because focus left the field leaves focus where the person put it, since pulling it back would trap them. Redraws go through `redraw()`, which keeps an open editor open (its save still carries the version it was drawn with) and keeps focus on the control at the same position, so a save in one cell never throws away typing in another or drops focus to the page. Results are said through `say()`, the note about a filter in the same sentence as the save. Viewers who cannot edit, trashed items, and tasks whose project is in the trash get plain text with no control. The per-row Edit form, the Notes row, and the table's Actions column are gone: the title is a plain link to the task page, which owns notes, comments, moving between projects, and trashing. A row that an edit moves out of the list's filters (a status filter on the project page; a task closed in My tasks, which hides closed tasks) stays until the list reloads, marked and announced, so nothing vanishes from under the cursor; the pager steps back one as before, since the edit may have moved the row past the loaded range. The owner-only rules stay: only the owner sees the Private cell as editable, and a private task's owner is changed only by its owner; making a task public still asks first.
- **The task page** (`task.html?id=`) shows every field, the notes, tags, project, comments, and the task's own activity (`GET /api/activity?item_type=task&item_id=`). A trashed task shows the trash notice with Restore; a missing id and an id the viewer cannot see render the same generic not-found page, so the page cannot tell anyone that a hidden task exists. Every task link in the UI (activity, search, My tasks, the overdue line, the trash) points here; the old `project.html#task-<id>` anchors are gone.
- **Trashing happens only on an item's own page** ("Trash this project", "Trash this task"), behind the confirm dialog, so a stray click in a list cannot trash anything. Restore stays on the Trash page and on the item's page.
- **Preferences live on the server** (`preferences` table, `GET`/`PATCH /api/me/preferences`, carried in the Me shape so pages get them with the call they already make), keyed by principal id so they work under every provider, dev and headers users included. They follow the person across devices, which a per-browser setting would not. Validation is against the config (themes), a fixed pair of labels, a boolean, and `Intl` for the time zone; site defaults come from `preference_defaults`, with UTC as the time zone unless a fork sets one. The browser remembers the last theme in `localStorage` (in try/catch) only to avoid a flash of the default before `/api/me` answers; the server copy is the truth. A chosen time zone decides "today" for overdue and how timestamps read; until one is chosen the browser keeps using the device's zone (`chosen` in the Preferences shape says which), so nobody sees UTC times without asking for them, while Claude follows the site default.
- **Every empty screen says what it is and what to do next**, in a sentence, with the obvious action beside it: the project list with only General (the under-construction sign, and "create your first project below, import one, or ask Claude"), an empty task table (the sign again), My tasks, What's New in each view (everything, for you, via Claude), the Trash, a search with no results (and where else to look), a profile with no tokens, an item with no comments, and a filtered list that matched nothing (with the way back: clear the filters, see every source, tick "Show closed tasks"). The sign is the one piece of nostalgia inside the content area; the sentences stay plain. A reader who cannot edit gets the statement without the call to action.
- **Import from Markdown** (`POST /api/projects/import`, the "Import from Markdown" section of the project list) reads exactly what the export writes, so a project can travel between copies of Taskscape, or be edited as text and brought back. The parser (`api/lib/markdown-import.js`) is pure and the creator (`api/lib/import.js`) plans first and writes second, in one transaction through the repo's `createIn` functions, so a later "duplicate project" can plan from a record instead of a file and run the same code. A dry run (`?dry_run=true`) returns the plan, which the UI shows before anything is created. Decisions: owner names map only on an exact, unique match among the people the importer may pick, else the item is the importer's, because a near match could hand someone else's name to a stranger; statuses must be configured, and every error names the field and the line, never the value; an item the file marks private stays private, and so becomes the importer's (an export of a private project says `Private: yes`, and publishing it by accident is the one thing an import must never do), while public items follow the privacy default or a "make private" switch; new tag names are counted in the notes because tags are public even when the import is not; a file is capped (a page of tasks, 20 tags per item, 50 new tag names, 20,000 characters per line) and one with two `## Tasks` lines is refused rather than guessed at, since a description is raw text anyone with edit rights could have written a heading into; notes are raw too, so the preview shows how long each task's notes are, and a line in them that matches another task's heading can still attach to that task (accepted: the export is for humans, and fencing it would change a format people already have); comments are counted and never imported, because an entry is signed by whoever writes it and a file cannot sign for anyone; the body is `text/markdown`, which no HTML form can send, so the cross-site rule holds without JSON. No MCP tool: Claude creates items one at a time already, and a bulk file write would let many things appear without the user seeing each.
- **Keyboard shortcuts** (`js/shortcuts.js`, on every signed-in page): `/` focuses search (from another page, goes to the project list and focuses it there), `n` focuses the new-project or new-task form, `?` opens a native `<dialog>` listing them, and `g` then `h`, `m`, `w`, `t` or `p` goes to Home, My tasks, What's New, Trash or Profile (`p` was added because the profile page holds the switch). Keys are ignored while focus is in a field, a select, a contenteditable element or an open dialog, and with Ctrl, Alt or Meta held, so typing never triggers one; no shortcut trashes or restores anything. They are single characters, so WCAG 2.1.4 needs a way to turn them off: that is the `shortcuts` preference, kept on the server with the others. `aria-keyshortcuts` marks the search box and the new-item fields while they are on (the `g` sequences are not marked: the attribute has no way to say "g then h").
- **Themes are files.** `theme` and `themes` in the config name the default and the choices; each is `public/css/theme-<name>.css`, and startup refuses a name without a file, so a fork adds a theme by dropping in CSS and a config entry, with no code change. Every page links the default; `js/theme.js` swaps the link to the person's choice. Two ship upstream: `toolbar` (the default) and `netscape` (the 1996 look, brought back as the second theme to keep the switching honest); company-specific themes belong in forks. A theme must style every selector the default styles, in light and dark, at phone width, with visible focus.
- **Comments are called "Comments" by default,** in headings, buttons, labels, empty text, activity wording and the export; the API and MCP always said so. "Guestbook" stays as a personal flavour (`comments_label`), since it was fun and costs only a vocabulary table (`commentWords()` in `js/guestbook.js`, whose file name stays).
- **For you** (What's New, "Show: For you", or `whats-new.html?for=me`) is `GET /api/activity?for=me`: other people's changes to the projects and tasks I own now, under the feed's read-time visibility. Ownership is read at query time, so handing an item over hands over its history, and an item that goes private to someone else drops out. The toolbar's What's New entry shows how many of those are newer than "last seen" (at most "20+"), and showing the For you view with Via: Anyone marks them seen (a Via filter may hide the newest one, so it does not). **"Last seen" lives in the browser**, in `localStorage` per user (`taskscape_for_you_seen:<user id>`), every access in try/catch: a server-side read marker would be a new table with writes outside the versioning rule and the activity log, for a badge. The cost is accepted: it does not follow anyone across browsers or devices, and clearing site data shows the recent entries as new again. Storage that refuses writes keeps the marker in memory for that page only.
- **Load more** on the project list, the task table, and My tasks (`js/pager.js`): the list routes return no total, so there is more exactly when a page comes back full (`items.length === limit`); a last page that happens to be full costs one empty request. Each list captures its query when it starts over, so later pages keep the sort and filters, and a response for a query that has since changed is dropped. Editing a row in the task table or My tasks (which can move it out of the loaded range) shifts the next offset back by one; a row that comes back a second time is dropped by id, so stepping back too far only repeats a request's worth of rows, never skips one. An empty last page puts focus on the last row. The button stays enabled while it loads (`aria-disabled`), so focus never falls to the page. The overdue line has its own query, so it holds however many pages are loaded.
- **Comments** (`js/guestbook.js`): a section under the task table for the project, and one on each task's page. Entries are oldest first, as plain text with the author and date; editors get an "Add a comment" form ("Sign the guestbook" under the Guestbook flavour), and the author gets Trash or Restore on their own entries. The section is built once per page, so a draft survives the page's other redraws. Trash and restore go through `attempt()`, and focus stays on the entry's button.
- **The header carries the person, not their name.** The old "Signed in as …" line is gone; the throbber at the top right is the avatar: a link to the profile page (accessible name "Your profile") showing the first letter of the signed-in name, drawn from a 5x7 bitmap font as SVG rects (`js/avatar.js`, through `svg()` in `dom.js`, so no markup string is ever parsed) over the theme's starfield, meteor and drift, with the site mark as the fallback before boot, on the sign-in page, and for a name the font cannot draw. Sign out stays in the header. The dev banner's select is labelled "Dev user".
- **The profile page** (`profile.html`, replacing the tokens page with no forwarding page) gathers everything about the person: name and initial, preferences, change password and active sign-ins for password sessions, MCP tokens, and their own recent activity (`GET /api/activity?actor=`).
- Padlock on private rows; confirm dialogs on trash, revoke, and privacy flips (flipping private names how many tasks move to General; flipping public warns that history becomes visible). General hides its privacy toggle and trash button.

History of the look: the 1996 Netscape theme came first, then a plain "nobody designed this" theme was the default from 2026-10-31; both were removed on 2026-11-01 along with the `theme` config key. On 2026-11-02 the key came back with a list and a per-person preference, and the Netscape theme returned as the second theme.

- Two MCP sessions both `get` a task and both `update` it with the same version: the second gets the conflict text with the current record and succeeds on retry.
- The counter on Website refresh increments on reload; `GET /api/projects` leaves it unchanged.
- Back up, edit a task, restore per README, and confirm the edit is gone.
- In a browser, every page in both themes, light and dark, at desktop and phone width, and once with the keyboard only (focus visible at every stop, every control named, `say()` announcing results, nothing moving under reduced motion), as a brand-new user as well as a seeded one. A scripted browser is fine for the sweep; the look still needs eyes.
